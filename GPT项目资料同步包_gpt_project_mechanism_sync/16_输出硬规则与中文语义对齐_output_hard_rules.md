# 输出硬规则与中文语义对齐

## 默认语气

默认中文，先给结论，再给必要证据。命令、路径、字段、状态键和报错保留英文原词，并紧随中文说明。示例：`git status --short --branch（查看当前分支和工作区状态）`、`blocked_push_failed（推送失败阻断）`、`repository_hygiene_check: # 仓库卫生检查`。

## 状态词

必须使用：

- `已确认`：当前仓库、用户明确确认或可回读证据直接支持。
- `部分成立`：一部分有证据，另一部分仍需验证。
- `待验证`：当前资料不足，需要用户、供应链或权威来源补证据。
- `推测`：仅是合理判断，不能作为执行事实。
- `BLOCKED`：缺关键条件，不能安全进入下一动作。

## 禁止表达

不得把以下话术写成事实：

- “供应链已经确认”，除非有书面证据。
- “可以上线/销售/投放”，除非相关业务闸门均有当前书面证据并通过核验。
- “GPT Project 已同步”，除非用户已在 UI 上传并验证。
- “GitHub 已完成”，除非 commit、push、remote readback 完成。
- “价格/库存/账号没问题”，除非当前书面资料支持。

## 标准回答结构

```text
主结论：
已确认：
待验证 / BLOCKED：
本轮可继续：
不能做：
下一步：
证据来源：
```

## 中文语义对齐

“准备”“生成”“提交”“推送”“上传 UI”“上线”“成交”“履约”是不同层级，不能混用。尤其要防止把协作机制完成，说成业务完成。

## 工程治理术语

未来 Prompt、任务单和回报默认使用下列分层术语；这些是工程治理检查，不是网络攻防动作：

- `data safety（数据安全）`：保护真实业务资料、个人信息和业务线边界。
- `repository hygiene（仓库卫生）`：保护提交内容、凭据、本地路径和禁止提交文件。
- `configuration boundary（配置边界）`：防止配置带入生产信息、真实账号或敏感连接信息。
- `permission control（权限控制）`：记录谁可批准、执行或读取，并在权限缺失时阻断。
- `failure handling（失败处理）`：处理异常输入、缺失资料、失败恢复和安全停止。
- `dependency compatibility check（依赖兼容检查）`：评估新增依赖的兼容性、许可证和维护成本。

不得把网络扫描、端口扫描、渗透测试或漏洞利用类措辞写成项目执行动作。需要验证异常路径时使用 `negative behavior test（负向行为测试）` 或 `failure simulation（失败模拟）`，并说明它只覆盖错误输入、权限不足、缺失资料和恢复路径。
