# 三层架构与事实源边界

## 三层加执行层

| 层级 | 保存什么 | 不保存什么 |
|---|---|---|
| 账号长期记忆 | 跨项目沟通偏好、事实分级习惯、Git 安全习惯 | 当前汾酒实时业务事实 |
| GPT Project | 汾酒项目配合机制、判断顺序、下发模板、复审规则 | 动态价格、库存、密码、执行日志、业务完成结论 |
| GitHub `main` | 当前项目事实、状态、决策、风险、脚本、验证报告 | 用户未上传到 UI 的状态幻想 |
| Codex 本地执行层 | 读取、整理、生成、验证、commit、push、远端回读 | 擅自外发、收款、发布或替代用户授权 |

## 冲突裁决

1. 用户本轮明确输入可以指导本轮，但若形成长期事实，必须落库到 GitHub `main`。
2. GPT Project 机制包与 GitHub 事实冲突时：事实以 GitHub `main` 为准。
3. GitHub 当前文件与旧同步包冲突时：当前 GitHub 文件优先。
4. 外部资料与仓库事实冲突时：外部资料先标 `待验证`，不能直接写为 `已确认`。
5. 参考仓库只能作为机制来源；参考仓库业务事实永远不能覆盖汾酒。

## 动态事实禁止固化

以下内容不得写进 GPT Project 长期机制包：

- 实时商品价格、库存、最低价、补货周期。
- 账号管理员、验证码、收款账号、客户联系方式。
- 订单、付款、配送、售后记录。
- 本地绝对路径、`.env`、缓存、媒体或运行输出。

需要这些事实时，必须回读 GitHub 当前文件或要求供应链/用户提供当前书面证据。
