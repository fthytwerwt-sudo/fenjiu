# P0-P1-P2 来源优先级与抗漂移机制

## 唯一定义

- `P0 = 用户本轮明确输入`：用户本轮目标、最新纠正、禁止项、验收标准，以及用户本轮明确提出的安全与合规红线。
- `P1 = GitHub main 当前事实、当前书面证据和当前验证证据`：GitHub main 当前文件、供应链当前书面资料、当前验证结果、commit / push / remote HEAD 和可回读业务证据。
- `P2 = 历史聊天、账号记忆、旧项目机制、外部资料和通用建议`：历史研究、参考仓库机制、旧项目经验、外部资料和可选优化。

唯一冲突顺序：

```text
P0 > P1 > P2
```

P0/P1/P2 只表示信息来源、约束来源和冲突优先级，不表示业务重要程度、风险级别、供应链缺口等级、技术优先级或执行阶段。

## 抗漂移检查

回答或下发 Codex 前先检查：

1. 是否把历史聊天、参考仓库或外部资料当成当前汾酒事实？如果是，降级为 P2。
2. 是否把用户本轮新纠正写成长期事实？如果是，必须先落库到 GitHub `main`，下一轮才能作为 P1。
3. 是否把商品、价格、库存、资质、账号、收款、履约或合规前置叫成 P0？如果是，改为 `business_gates（业务闸门）`。
4. 是否把技术完成、文件生成或脚本通过写成业务上线？如果是，拆分为技术状态和业务状态。
5. 是否把参考项目机制连同参考项目业务事实一起迁入？如果是，只保留机制，删除业务事实。

## business_gates（业务闸门）

以下条件不是 P0/P1/P2 等级，而是外部执行前必须满足的业务闸门：

- SKU、规格、商品素材。
- 价格、最低价、有效期。
- 库存、补货、供应稳定性。
- 当地主体、品牌授权、资质或合法销售证据。
- 账号主体、管理员权限和认证支持。
- 收款、仓储、配送、退换货、售后和负责人。
- TikTok 酒类内容、广告和转化边界。
- 用户明确授权进入公开发布、投放、收款、下单、发货或真实售后。

业务闸门缺少当前书面证据时，状态统一为 `BLOCKED`。

## hard_constraints（硬约束）

不得泄露密钥，不得编造业务事实，不得混入海鲜事实，不得绕过酒类合规，不得向错误仓库推送，不得把用户尚未上传 GPT Project UI 写成已生效。
