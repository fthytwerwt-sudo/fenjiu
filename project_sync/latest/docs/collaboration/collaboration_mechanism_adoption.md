# 协作机制采用对照｜参考机制到汾酒项目

本项目只借鉴参考仓库的协作机制，不继承参考项目的业务内容、客户资料、产品信息、绝对路径、账号、任务、结论或秘密。

## 审计边界

- **目标仓库**：fthytwerwt-sudo/fenjiu。
- **本地资料**：包含汾酒与海鲜两条业务线、研究源、文档脚本、媒体、QA 与生成物；只可按本项目事实源地图定向读取。
- **迁移原则**：保留入口、状态、决策、交接和轻量同步机制；不复制外部项目的业务内容或本地结构。

## 采用对照

| 机制 | 解决的问题 | 本项目采用方式 | 当前边界 |
|---|---|---|---|
| 固定入口与阅读顺序 | 新 Agent 误读范围或事实源 | AGENTS、PROJECT_ENTRY、BUSINESS_STATUS、CURRENT_STATUS、SOURCE_OF_TRUTH、COLLABORATION_STATUS | 业务状态与协作状态分开维护 |
| 短状态与执行历史 | 新会话不知道现在到哪 | CURRENT_STATUS 只路由；业务和协作各有详细状态 | 机制记录不等于业务完成 |
| allowlist 同步包 | 交接资料过多、敏感或不可验证 | 轻量文件、哈希、ZIP、verify 与新会话模拟 | 不记录本机路径或真实排除清单 |
| 事实源优先级与旧资料降级 | 多份旧研究互相冲突 | SOURCE_OF_TRUTH 标识历史输入与当前范围 | 原始研究保留，不重写 |
| 任务卡与交接模板 | 目标、边界、验收不完整 | 任务、会话和执行报告模板 | 外部动作仍需用户和合规授权 |
| 决策记录 | 关键取舍被聊天历史吞没 | 业务决定和协作决定分区记录 | 决策不是供应链回执或许可 |
| 多 Agent 路由 | 并行时覆盖核心状态 | 只读工作可并行，核心状态由明确负责人整合 | 不借此扩大业务权限 |

## 简化原则

1. 入口先讲当前 TikTok 业务和供应链启动阶段，再讲协作机制。
2. 同步包只收录理解项目所需的轻量内容，不复制原始业务文件或大文件。
3. 使用 CONFIRMED、INFERRED、UNKNOWN、BLOCKED、SUPERSEDED 区分事实。
4. 先审计再修改；不因 Private、提交或测试通过而跳过脱敏或业务闸门。
5. 海鲜独立处理；外部传播、平台、支付、订单与履约均以当前书面证据和人工授权为准。
